결과 읽는 법
판정
이 보고서는 성공·실패를 판정하지 않습니다. 모든 Bidmad 모듈이 연동됐다고 가정하고 점검한 사실만 보여 주며, 판단은 보고서를 읽는 사람이 합니다.
확인됨
원래 이름으로 해석됨 (L2 항목은 클래스 초기화까지, L3 항목은 실제 호출까지 성공 — 상세의 l3=ok, 기대값과 다르면 l3-unexpected).
찾을 수 없음
원래 이름으로 해석되지 않음 — 클래스·멤버·서비스 파일·구현체·.so 가 없거나 이름이 바뀜.
오류
이름은 찾았지만 클래스 초기화(L2) 또는 실제 호출(L3)에서 예외가 났거나 점검기 자체가 예외를 냄. L3 상세: l3-threw(대상 코드가 던짐 — 실행 시 크래시 신호), l3-link(호출 링크 실패), l3-args(점검기 인자·스펙 문제).
미포함
목록의 모든 항목이 원래 이름으로 클래스를 찾지 못함. 기기에서는 연동하지 않음과 연동했지만 이름이 바뀜을 구분할 수 없습니다. 확인된 것으로 세지 않으며, 아래 정황을 보고 판단하세요.
services-file
정황: META-INF/services/<원래 인터페이스 이름> 파일이 앱에 있음 → 라이브러리는 들어 있고 인터페이스 이름이 바뀌었을 가능성이 큼 (예: AppSuit 의 Ktor).
manifest-declared
정황: 설치된 앱 매니페스트에 원래 이름으로 선언돼 있음 → 컴포넌트 클래스 이름만 바뀌었을 가능성이 큼 (실행 시 크래시 위험).
linked-as=…
정황: 점검기가 컴파일 시점에 연결한 bidmad 클래스가 다른 이름으로 해석됨 → bidmad 는 들어 있고 이름이 바뀜.
services-renamed=…
정황: 원래 이름의 services 파일은 없지만 다른 services 파일의 내용이 이 항목의 구현체를 가리킴 → 라이브러리는 들어 있고 SPI 인터페이스 이름이 그 이름으로 바뀜 (R8/AppSuit). 뒤의 값이 바뀐 인터페이스 이름.
경고
LOADER: 앱 기본 클래스 로더가 아닌 로더에서 로드됨. SPLIT: 같은 패키지 클래스가 여러 로더로 갈라짐. SPI_UNRESOLVED: META-INF/services 가 선언한 구현체를 원래 이름으로 로드할 수 없음 → ServiceLoader 가 provider 를 못 만들어 그 경로 실행 시 크래시 위험.
건너뜀
지원하지 않는 항목이거나 10초 점검 예산을 넘겨 점검하지 못함.
L1 / L2 / L3
L1: 이름 해석과 멤버 조회(읽기 전용). L2: 클래스 초기화까지 실행. L3: 멤버를 목록이 준 인자로 실제 호출 — 파트너 SDK 진입점이 난독화 후에도 호출·동작하는지 확인. 반환값은 타입·요약만 남기고 원문은 기록하지 않음.
